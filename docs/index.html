A specification nobody checks is a wish.

Most teams already write requirements. They live in a wiki, drift from the code within a sprint, and nothing fails when they disagree. Point a coding agent at that and you have automated the drift — at the speed of an agent.

Specgate makes the specification a thing that can be wrong: every requirement has a scenario, every scenario a test that names it, and specgate check fails the moment one link breaks. Then — and only then — an agent is worth pointing at it.

The lifecycle

From a brief to a proven requirement, in ten steps.

Specify, build, prove. The order matters: nothing is built before it is specified, and nothing counts as done until the gate has checked it. Follow one requirement through the whole path.

  1. Specify
  2. Build
  3. Prove

  1. docs/brief.md

    Keep the client's words in the repository

    The brief goes in as it arrived. A short front matter names who uses the product and through which surfaces — the checklist uses it to ask for a scenario per actor and screen.

  2. specgate change new

    One module at a time, as a change

    You or your agent write requirements and Gherkin scenarios for one module. Small enough to review in one sitting — the checklist stops at 25 requirements.

  3. specgate draft --check

    Every value comes from somewhere

    Twelve rules. A number the brief never gave is either written down as an assumption or becomes a question — and the requirement it blocks waits for the client instead of being guessed.

  4. specgate change archive

    The specification lands in one step

    Requirements, one feature file each, and their rows in the traceability matrix. Everything arrives as Draft, so the spec can merge before any code exists.

  5. specgate status

    What to build, in order

    What is open, ordered by what blocks what — and the single next command to run. Requirements waiting for an answer are listed apart, with the question that blocks them.

  6. specgate harness run

    One requirement, one worktree, one agent

    The harness hands each pending requirement to your agent in its own git worktree, runs the gate on the result, and stops if the gate says no. A person can do the same step by hand: write the test, write the code.

  7. harness/REQ-…

    You review, you merge

    One branch per requirement, each with its own test. The harness never merges: what to keep is a judgement, and it stays yours.

  8. specgate done

    Marked only when it is true

    Runs the gate for that requirement and marks it Implemented only if it passes. While it fails, it writes nothing — and what it closes, CI will not reopen.

  9. specgate check

    The whole chain, on every pull request

    The specification, the matrix, then your own tests. This is what CI runs, and the last thing you run before asking for review.

  10. specgate report

    One page for the product owner

    Done, pending, missing a test, waiting for an answer — per requirement, generated from the same matrix the gate enforces.

Waiting for an answer A requirement blocked by an open question skips steps 6–8: the harness will not build it and done refuses it until the client answers. Then it rejoins the queue at step 5.

Why teams pick it

Six things it will not let slide.

A gate that can't be talked round

done writes nothing while the gate fails. An agent that rewrites a scenario to pass its own test fails the attempt, with the diff fed back.

Ambiguity becomes a question

What the brief cannot answer is asked, not guessed. The requirement it blocks waits for an answer — no person and no agent can close it in the meantime.

From a brief, honestly

draft --check lists every value nobody gave you. On a five-line brief that list is long — and it is exactly the conversation to have with the client.

Any agent, unattended

The harness drives any CLI that takes a prompt, one git worktree per requirement. It never talks to a model itself, and it never merges.

Your stack, your tests

The gate runs the test command you already have. Proven on Node, Spring Boot and Quarkus; it adopts a repository without touching a line of its code.

Traceability without bookkeeping

A test that mentions REQ-007 is the link. The matrix is derived from what your tests say, so it cannot drift from them.

Unattended delivery

Hand the loop to an agent — in sequence.

specgate harness run takes each pending requirement in its own git worktree, hands your agent a prompt built from its Gherkin, runs the gate on the result, and commits only if it is green. It never merges — the branch is yours to merge or throw away. The agent is any shell command; there is no runtime or SDK.

Every day

After the first draft, five commands.

The same five whether a person or an agent is driving — as commands, as slash commands, or as MCP tools. A small change skips the draft entirely.

specgate init looks before it writes: where there is code it adopts the repository, where there is none it scaffolds a project. specgate ci init detects GitHub, GitLab, Azure or Jenkins and writes the job.

  1. 1

    specgate status

    What is open and what blocks what — the single next command to run.

  2. 2

    specgate new

    A requirement and its tagged scenario, in one step — for the change too small to need a draft.

  3. 3

    // REQ-007

    Write the test and the code. A test that mentions the requirement is the link — nothing to declare.

  4. 4

    specgate done

    Checks first; marks it Implemented only if it passes.

  5. 5

    specgate check

    The whole gate, then your tests — what CI runs.

A status is a promise. The gate collects on it.

Green on the day you adopt it, stricter with every requirement you deliver — and a green run always says what it did not check.

  1. Draft

    Owes nothing

    Except honesty: no scenario without steps, no keyword Cucumber would read as prose.

  2. Needs Clarification

    Owes an answer

    From the client. Until then the harness skips it and done refuses it.

  3. In progress

    Owes a test

    One that mentions it — the moment work on it has started.

  4. Implemented · Verified · Released

    Owes everything

    Every file it points at exists, its scenario has real steps, and the suite is green.

Evidence

Every check is a scar.

Each one exists because the loop was caught approving work it had not checked — found by running the tool on real projects, and now a test that fails when the guard is removed.

  • Every test was green and the application did not boot — on the core-banking pilot. Specgate now suggests a startup test for JVM stacks, and the harness asks for one on Spring.
  • An agent that could not pass a scenario rewrote the scenario and got 1 passed · 0 failed. Now touching spec.md or features/** fails the attempt, with the diff fed back.
  • done closed a requirement that was still waiting for the client, with no test behind it. Now it refuses, and status lists it apart with the question that blocks it.
  • 27 of 28 scenarios in the starter packs executed nothing. Gherkin keywords are case-sensitive, so GIVEN parsed as prose — and an empty scenario passes. The gate now refuses a scenario Cucumber would see as empty.

Questions teams ask first.

All questions →

Does it work on a repository that already exists?

Yes, that is the common case. specgate init adopts it in place without touching your code, and the gate is green the same day: a Draft requirement owes nothing yet.

Is it safe to let an agent write the draft from a brief?

Safer than letting it write the code from the brief. The checklist lists every value the agent added, and anything nobody can answer becomes a question that blocks its requirement. You review a short list, not the whole draft.

Does every pull request need a new requirement?

No. A bugfix or a refactor that does not change contracted behaviour adds none; the gate only asks for what delivered requirements owe.

Can the agent rewrite the spec to pass its own test?

Not quietly. Over MCP, tools that write the specification refuse unless a change is open; in the harness, touching the spec fails the attempt.

Will the harness merge things for me?

Never. It leaves one branch per requirement and stops. Merging is a judgement, and it stays yours.
