A specification nobody checks is a wish.

Most teams already write requirements. They live in a wiki, drift from the code within a sprint, and nothing fails when they disagree. Point a coding agent at that and you have automated the drift — at the speed of an agent.

Specgate makes the specification a thing that can be wrong: every requirement has a scenario — a concrete example in Gherkin — every scenario a test that names it, and specgate check fails the moment one link breaks. Then, and only then, an agent is worth pointing at it.

The pipeline

Four layers between a piece of work and a shipped requirement.

  1. 01

    The source

    Where the work comes from: a change you describe, a brief for a new product, or a Jira story with acceptance criteria. Each opens a change — a folder that holds the work until it is built.

    specgate propose
  2. 02

    The checked requirements

    You or your agent write the requirements and scenarios the change adds. Every value the brief or ticket never gave is listed as an assumption or becomes a question.

    --from-brief · --from-ticket
  3. 03

    The tests

    A test that names REQ-007 is the link. The table of links — the traceability matrix — is generated from what your tests say; nobody edits it.

    // REQ-007
  4. 04

    The gate

    The specification, its links to tests and your own suite. A requirement is done only when all three pass — for a person, an agent or CI. A change is archived into the specification once all of its requirements are.

    specgate apply · archive · check

Your journey

Five phases, from your first command to a gate in CI.

Work comes in three ways — a change you describe (specgate propose <change-id>), a brief for a new product (specgate propose --from-brief), or a Jira story (specgate propose --from-ticket <KEY>) — and follows one lifecycle: propose, build and apply each requirement, archive, open the pull request. From a Jira ticket →

Pick where you start. Each phase says who does the work — you, your agent or the gate — what to run, what you see, and what you have when it is over.

  1. Phase 1 about 5 minutes

    • You
    • The gate
    01

    Create the project with your own tools — npm init, Spring Initializr, cargo new — then let Specgate set itself up in place. It writes specifications, never application code.

    + spec.md
    + AGENTS.md
    + docs/specs/traceability.md
$ specgate config set test_cmd "node --test"
  ✔  test_cmd = node --test
$ specgate check
  ✔  Specification   validate --strict
  ✔  Tests           node --test
  ✔  Gate passed

    You now have a specification, an agent contract every coding agent reads, and a gate that already runs your tests.

Run the same command again to check the draft: it stops on any value the brief never gave. What only the client can answer becomes a question, not a guess.     You now have requirements and Gherkin scenarios a person reviewed, every invented value either sourced or asked about — in an open change, counted by status, ready to build.

  5. Phase 5 four verbs

    • You
    • Your agent
    • The gate
    05

    Put the gate on every pull request — the specification, then your tests. This is what CI runs, and it is the same command you run locally. From then on the loop is four verbs: specgate propose a change — from your own words, the brief or a Jira ticket — write its delta (the requirements it adds) and a test that names each requirement, specgate apply it, specgate archive the change when the last one is in, and open the pull request. specgate status always says where you are. In a small project, specgate new adds a single requirement without a change.

    $ specgate ci init --provider github
    + .github/workflows/spec-gate.yml

# a Jira story: its own change and branch, feature/KAN-13-…

Why teams pick it

Six things it will not let slide.

A gate that can't be talked round

apply writes nothing while the gate fails. An agent that rewrites a scenario to pass its own test fails the attempt, with the diff fed back.

Ambiguity becomes a question

What the brief cannot answer is asked, not guessed. The requirement it blocks waits for an answer — no person and no agent can close it in the meantime.

From a brief, honestly

specgate propose --from-brief lists every value nobody gave you. On a five-line brief that list is long — and it is exactly the conversation to have with the client.

Any agent, unattended

The harness drives any CLI that takes a prompt, one git worktree per requirement. It never talks to a model itself, and merges only when you ask for a --chain.

Your stack, your tests

The gate runs the test command you already have. Proven on Node, Spring Boot and Quarkus; it adopts a repository without touching a line of its code.

Traceability without bookkeeping

A test that mentions REQ-007 is the link. The matrix is derived from what your tests say, so it cannot drift from them.

The harness · unattended delivery

Your agent builds.
The gate decides. You merge.

specgate harness run takes each pending requirement in its own git worktree, hands your agent a prompt built from its Gherkin, runs the gate on the result, and commits only if it is green. It does not merge — the branch is yours to merge or throw away — unless you run a --chain, which merges each green requirement and stops at the first red one. The agent is any shell command; there is no runtime or SDK. specgate studio shows the run at /live, as it happens (the harness).

Evidence

Every check is a scar.

Each one exists because the loop was caught approving work it had not checked — found by running the tool on real projects, and now a test that fails when the guard is removed.

  • Every test was green and the application did not boot — on the core-banking pilot. Specgate now suggests a startup test for JVM stacks, and the harness asks for one on Spring.
  • An agent that could not pass a scenario rewrote the scenario and got 1 passed · 0 failed. Now touching spec.md or features/** fails the attempt, with the diff fed back.
  • The command that marks a requirement done, apply, closed one still waiting for the client, with no test behind it. Now it refuses, and status lists it apart with the question that blocks it.
  • 27 of 28 scenarios in the starter packs executed nothing. Gherkin keywords are case-sensitive, so GIVEN parsed as prose — and an empty scenario passes. The gate now refuses a scenario Cucumber would see as empty.

If you know OpenSpec

OpenSpec records what was done. Specgate proves it.

OpenSpec made the change loop popular, and it is the tool to look at first. Specgate uses the same three verbs — propose, apply, archive — with a gate under each. OpenSpec checks the shape of your specification and leaves the proof to you. Specgate is the proof.

When an agent says “done”

OpenSpecArchive asks to continue if tasks are unticked; --yes skips it. Verify is an AI review that “won't block archive”.

Specgateapply refuses until a test names the requirement and your suite passes; archive refuses while one is pending, and no flag skips it.

When the draft comes from a client's brief

OpenSpecThe prompt asks the agent not to invent intent. Nothing checks it.

Specgatespecgate propose --from-brief stops on a fee, limit or number the brief never stated.

When only the client can answer

OpenSpecThe agent records an assumption and carries on.

SpecgateNeeds Clarification blocks building and closing it until someone answers.

When you hand the work to an agent

OpenSpec/opsx:apply works through the tasks in your session.

Specgateharness run: one branch per requirement, the gate after each attempt; it merges only with --chain, and only what passed.

Where OpenSpec is ahead: far more users, 30+ agent integrations against our 10, customisable workflows, and no tests required to start. If you want the change loop and nothing else, it is the better tool. Already on it? Keep it, and let specgate verify gate what it archives.

Questions teams ask first.

All questions →

Does it work on a repository that already exists?

Yes, that is the common case. specgate init adopts it in place without touching your code, and the gate is green the same day: a Draft requirement owes nothing yet.

Is it safe to let an agent write the draft from a brief?

Safer than letting it write the code from the brief. The checklist lists every value the agent added, and anything nobody can answer becomes a question that blocks its requirement. You review a short list, not the whole draft.

Can a Jira ticket be the starting point?

Yes. specgate propose --from-ticket KAN-13 checks the story is ready — acceptance criteria present, measurable, small enough — then opens a change from it and pushes its branch. Specgate only reads Jira; the board moves through your own Jira automation. From a Jira ticket →

Does every pull request need a new requirement?

No. A bugfix or a refactor that does not change contracted behaviour adds none; the gate only asks for what delivered requirements owe.

Can the agent rewrite the spec to pass its own test?

Not quietly. Over MCP, tools that write the specification refuse unless a change is open; in the harness, touching the spec fails the attempt.

Will the harness merge things for me?

Not unless you ask. By default it leaves one branch per requirement and stops: merging is a judgement, and it stays yours. With --chain it merges each requirement that passed the gate, runs the gate again on the merge, and stops at the first failure.
