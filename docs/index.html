A specification nobody checks is a wish.

Most teams already write requirements. They live in a wiki, drift from the code within a sprint, and nothing fails when they disagree. Point a coding agent at that and you have automated the drift.

Specgate makes the specification a thing that can be wrong: every requirement has a scenario, every scenario a test that names it, and specgate check fails the moment one link breaks. Then — and only then — an agent is worth pointing at it.

The daily loop

Five commands. That is the whole method.

The same five whether a person or an agent is driving — as commands, as slash commands, or as MCP tools. Mentioning a requirement in a test is the link; the matrix writes itself.

  1. 1

    specgate status

    What is open, ordered by what blocks what — and the single next command to run.

  2. 2

    specgate new

    A requirement and its tagged scenario, in one step. You rewrite the sentence and the three placeholders.

  3. 3

    // REQ-007

    Write the test and the code. A test that mentions the requirement is the link — nothing to declare.

  4. 4

    specgate done

    Runs the gate for that requirement and marks it Implemented only if it passes. What it closes, CI will not reopen.

  5. 5

    specgate check

    The whole gate, then your tests. This is what CI runs, and the last thing you run before asking for review.

A status is a promise. The gate collects on it.

Green on the day you adopt it, stricter with every requirement you deliver — and a green run always says what it did not check.

The MCP server →

Unattended delivery

Hand the loop to an agent.

specgate harness run takes each pending requirement in its own git worktree, runs the gate on the result, and stops if the gate says no. It never merges — the branch is yours to merge or throw away. The agent is any shell command; there is no runtime or SDK.

Evidence

Every check is a scar.

Each one exists because the loop was caught approving work it had not checked — found by running the tool on real projects, and now a test that fails when the guard is removed.

  • 27 of 28 scenarios in the shipped domain packs executed nothing. Gherkin keywords are case-sensitive, so GIVEN parsed as prose — and an empty scenario passes. The gate now refuses a scenario Cucumber would see as empty.
  • An agent that could not pass a scenario rewrote the scenario and got 1 passed · 0 failed. Now touching spec.md or features/** fails the attempt, with the diff fed back.
  • done printed ✔ over a scenario of template steps and no test, and the next check — the one in CI — failed. Now done runs the gate first and writes nothing while it fails.

Questions teams ask first.

All questions →

Does it work on a repository that already exists?

Yes, that is the common case. specgate init adopts it in place without touching your code, and the gate is green the same day: a Draft requirement owes nothing yet.

Does every pull request need a new requirement?

No. A bugfix or a refactor that does not change contracted behaviour adds none; the gate only asks for what delivered requirements owe.

Do we have to use DDD?

No. Patterns are optional; principles are not. Pick an architecture profile and you get only the vocabulary it declares.

Can the agent rewrite the spec to pass its own test?

Not quietly. Over MCP, tools that write the specification refuse unless a change is open; in the harness, touching the spec fails the attempt.

Will the harness merge things for me?

Never. It leaves one branch per requirement and stops. Merging is a judgement, and it stays yours.
