A specification nobody checks is a wish.

Most teams already write requirements. They live in a wiki, drift from the code within a sprint, and nothing fails when they disagree. Point a coding agent at that and you have automated the drift — at the speed of an agent.

Specgate makes the specification a thing that can be wrong: every requirement has a scenario, every scenario a test that names it, and specgate check fails the moment one link breaks. Then — and only then — an agent is worth pointing at it.

Your journey

Five phases, from your first command to a gate in CI.

Pick where you start. Each phase says who does the work — you, your agent or the gate — what to run, what you see, and what you have when it is over.

  1. 1

    Phase 1 · about 5 minutes

    Install and set up

    • You
    • The gate

    Create the project with your own tools — npm init, Spring Initializr, cargo new — then let Specgate set itself up in place. It writes specifications, never application code.

    $ npx @rsaglobaltech/specgate@latest init
…write spec.md
…write AGENTS.md
…write docs/specs/traceability.md
$ specgate config set test_cmd "node --test"
  ✔  test_cmd = node --test
$ specgate check
✔  Gate passed — the specification and `node --test`

    You now have a specification, an agent contract every coding agent reads, and a gate that already runs your tests.

  2. 2

    Phase 2 · an hour per module

    From the brief to a checked spec

    • You
    • Your agent
    • The gate

    Save the client's brief — or your own plan — as docs/brief.md. specgate draft explains the four fields it needs on top (your agent can propose them), then names the next module; specgate draft bookings opens it and writes the prompt for your agent. Run it again and it stops on anything the brief never said. What only the client can answer becomes a question, not a guess.

    $ specgate draft
  Modules
    ○ bookings  not started
$ specgate draft bookings
  ✔ Draft draft-bookings opened, linked to docs/brief.md
    Draft the bookings module: follow …/DRAFTING.md
# paste that into your agent — or add --agent "claude -p"
$ specgate draft bookings
  ✖  D6_unlisted_value  SCN-005 states "5", which is not in the brief
# the fee becomes a question for the client
  ✔  Ready to review.
$ specgate change archive draft-bookings
  ✔ Archived as 2026-01-01-draft-bookings

    You now have requirements and Gherkin scenarios a person reviewed, every invented value either sourced or asked about.

    Write the brief, step by step → From scratch · phase 2, step by step →
  3. 3

    Phase 3 · per requirement

    Build the first requirement

    • You
    • Your agent

    specgate status names the single next command to run. Write the test first and name the requirement in it — that mention is the link. Build it by hand, or hand it to the harness: one branch per requirement, and it stops if the gate says no.

    $ specgate status
  To do
    REQ-002   A member books a court for one hour
  Waiting for an answer
    REQ-004   A member cancels a booking   an answer to Q1
$ node --test
✔ REQ-002 SCN-002: booking a free court lasts one hour
$ specgate harness run --req REQ-003
your agent, in its own git worktree

    You now have code and a test that names its requirement — on a branch, waiting for your review.

    From scratch · phase 3, step by step →
  4. 4

    Phase 4 · seconds

    Prove it

    • The gate

    done runs the gate for that requirement and marks it Implemented only if it passes. A requirement waiting for the client cannot be closed. report turns it all into one page for the product owner.

    $ specgate done REQ-002
✔  REQ-002 → Implemented (1 row updated)
$ specgate done REQ-004
✖  REQ-004 not marked Implemented: REQ-004 is waiting
   for an answer (Needs Clarification).
$ specgate report --out report.html
📊 Wrote report.html — 25% implemented (1/4).

    You now have a requirement marked done because a test proved it — and a page that says where the product stands.

    From scratch · phase 4, step by step →
  5. 5

    Phase 5 · five commands

    Every day

    • You
    • Your agent
    • The gate

    Put the gate on every pull request — the specification, then your tests. This is what CI runs, and it is the same command you run locally. From then on the loop is specgate status, specgate new, a test that names the requirement, specgate done, specgate check — by hand, as slash commands, or as MCP tools.

    $ specgate ci init --provider github
  write .github/workflows/spec-gate.yml
  ✅ CI gate installed.
$ specgate new "A member sees which courts are free on a day"
✔  REQ-005 A member sees which courts are free on a day (Draft)
$ specgate status
  Next  specgate done REQ-005  — once a test mentions REQ-005

    You now have a gate on every pull request, and a loop small enough to remember.

  1. 1

    Phase 1 · about 5 minutes

    Adopt, touching no code

    • You
    • The gate

    onboard reads your build files and proposes the capabilities your layout already implies. init adopts the repository in place — specifications only, not a line of your code — and the gate runs your existing tests.

     · Invoices    src/invoices   (2 files)
     · Customers   src/customers  (1 files)
$ specgate init
  Existing code found (package.json) — adopting this
  repository in place. Nothing in your code is touched.
$ specgate check
✔  Gate passed

    You now have a specification seeded from your own layout, an agent contract, and a green gate over the tests you already had.

  2. 2

    Phase 2 · minutes per behaviour

    Write down what you rely on

    • You
    • Your agent

    Don't back-fill everything. Pick one behaviour your users depend on and write it as a requirement with a real example — the numbers your code already produces.

    $ specgate new "An invoice total is rounded to the cent"
✔  REQ-004 An invoice total is rounded to the cent (Draft)
$ cat features/an-invoice-total-is-rounded-to.feature
  @REQ-004 @SCN-002
  Scenario: Three lines at 21% VAT
    When its total is computed at 21% VAT
    Then the total is 35.56

    You now have one behaviour written down as a requirement and a scenario anyone can read.

    Existing project · phase 2, step by step →
  3. 3

    Phase 3 · minutes

    Close the first requirement

    • You
    • The gate

    done refuses while nothing proves it. Name the requirement in the test you already have — that is the whole link — and run it again. It marks it Implemented only if it passes.

    $ specgate done REQ-004
  [TDD-1] Test artifact is TBD but status is 'Implemented'
✖  REQ-004 not marked Implemented: validation failed.
test("REQ-004: three lines at 21% VAT are rounded…")
$ specgate done REQ-004
✔  REQ-004 → Implemented (1 row updated)

    You now have your first requirement proved by a test that already existed.

    Existing project · phase 3, step by step →
  4. 4

    Phase 4 · one commit

    Put the gate in CI

    • The gate

    Requirements still in Draft owe nothing yet, so you don't have to fix the past first. This is what CI runs on every pull request: the specification, then your tests.

    $ specgate ci init --provider github
  write .github/workflows/spec-gate.yml
$ specgate check
  Strict TDD gate: passed (2 row(s) exempt — still
  Draft, so not checked)
✔  Gate passed

    You now have a gate that protects what you have proved and ignores what you haven't written down yet.

Why teams pick it

Six things it will not let slide.

A gate that can't be talked round

done writes nothing while the gate fails. An agent that rewrites a scenario to pass its own test fails the attempt, with the diff fed back.

Ambiguity becomes a question

What the brief cannot answer is asked, not guessed. The requirement it blocks waits for an answer — no person and no agent can close it in the meantime.

From a brief, honestly

specgate draft lists every value nobody gave you. On a five-line brief that list is long — and it is exactly the conversation to have with the client.

Any agent, unattended

The harness drives any CLI that takes a prompt, one git worktree per requirement. It never talks to a model itself, and it never merges.

Your stack, your tests

The gate runs the test command you already have. Proven on Node, Spring Boot and Quarkus; it adopts a repository without touching a line of its code.

Traceability without bookkeeping

A test that mentions REQ-007 is the link. The matrix is derived from what your tests say, so it cannot drift from them.

Unattended delivery

Hand the loop to an agent — in sequence.

specgate harness run takes each pending requirement in its own git worktree, hands your agent a prompt built from its Gherkin, runs the gate on the result, and commits only if it is green. It never merges — the branch is yours to merge or throw away. The agent is any shell command; there is no runtime or SDK.

A status is a promise. The gate collects on it.

Green on the day you adopt it, stricter with every requirement you deliver — and a green run always says what it did not check.

  1. Draft

    Owes nothing

    Except honesty: no scenario without steps, no keyword Cucumber would read as prose.

  2. Needs Clarification

    Owes an answer

    From the client. Until then the harness skips it and done refuses it.

  3. In progress

    Owes a test

    One that mentions it — the moment work on it has started.

  4. Implemented · Verified · Released

    Owes everything

    Every file it points at exists, its scenario has real steps, and the suite is green.

Evidence

Every check is a scar.

Each one exists because the loop was caught approving work it had not checked — found by running the tool on real projects, and now a test that fails when the guard is removed.

  • Every test was green and the application did not boot — on the core-banking pilot. Specgate now suggests a startup test for JVM stacks, and the harness asks for one on Spring.
  • An agent that could not pass a scenario rewrote the scenario and got 1 passed · 0 failed. Now touching spec.md or features/** fails the attempt, with the diff fed back.
  • done closed a requirement that was still waiting for the client, with no test behind it. Now it refuses, and status lists it apart with the question that blocks it.
  • 27 of 28 scenarios in the starter packs executed nothing. Gherkin keywords are case-sensitive, so GIVEN parsed as prose — and an empty scenario passes. The gate now refuses a scenario Cucumber would see as empty.

Questions teams ask first.

All questions →

Does it work on a repository that already exists?

Yes, that is the common case. specgate init adopts it in place without touching your code, and the gate is green the same day: a Draft requirement owes nothing yet.

Is it safe to let an agent write the draft from a brief?

Safer than letting it write the code from the brief. The checklist lists every value the agent added, and anything nobody can answer becomes a question that blocks its requirement. You review a short list, not the whole draft.

Does every pull request need a new requirement?

No. A bugfix or a refactor that does not change contracted behaviour adds none; the gate only asks for what delivered requirements owe.

Can the agent rewrite the spec to pass its own test?

Not quietly. Over MCP, tools that write the specification refuse unless a change is open; in the harness, touching the spec fails the attempt.

Will the harness merge things for me?

Never. It leaves one branch per requirement and stops. Merging is a judgement, and it stays yours.
