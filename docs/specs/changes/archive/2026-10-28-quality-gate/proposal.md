# Proposal: quality-gate

## Intent

The gate proves a requirement is specified, linked and tested, and with
`arch_cmd` that its code sits where the architecture says. It does not prove
that the tests would catch a bug, that the new code is covered, that it is
secure, or that it stays maintainable — the ways code written by an agent
most often fails while every test is green. The person this serves develops
mainly in Java (Maven or Gradle, Spring Boot or Quarkus, often generated by
forja) and also in Node.js with React; both must be first-class.

The decision is ADR-0040. This change delivers it.

## Scope

In scope:

- `checks:` in `harness.config.yaml`: named commands, each with when it runs
  (`attempt`, `end`, `ci`), whether it gates or only advises, and the SARIF or
  report file it writes.
- The checks run by `specgate check`, `specgate done` and the harness gate; an
  `attempt` check's failure fed back to the agent with its findings.
- A baseline of findings (`specgate quality baseline`): only findings a change
  adds fail it; SARIF fingerprints so moved code is not new code. This also
  closes ADR-0028's pending points 3 and 4 for `arch_cmd`.
- Diff coverage computed by Specgate from JaCoCo XML, LCOV or Cobertura and
  `git diff`, with a threshold.
- Mutation score of the changed code read from PIT `mutations.xml` or
  StrykerJS `mutation.json`, with a threshold.
- Levels `quality: basic | strict | custom` and presets per stack — Maven,
  Gradle, npm/pnpm — written by `harness init`, `adopt`, `specgate quality
  init` and the studio's new-project step.
- Security presets: osv-scanner, OWASP Dependency-Check, Semgrep, gitleaks,
  FindSecBugs by default (free, offline-capable); SonarQube/SonarCloud, Snyk
  and Aikido as platform presets whose tokens come from the environment.
- `review_profile` / `adversary_profile` usable as `end` checks.
- Results per requirement in the harness run record, the matrix, `harness
  report`, `/live` and the studio's report and Calidad card.
- Documentation of all of it (see `docs-impact.md`).

Out of scope:

- Running any tool Specgate does not find in the project's build: a preset
  for a missing tool is written commented, with the line to add it.
- Fixing an existing codebase's debt: the baseline records it; reducing it is
  the team's work.
- Hosting or configuring a SonarQube server, a Snyk or Aikido organisation.
- Languages other than Java and TypeScript/JavaScript in this change (.NET,
  Python, Go follow the same mechanism later; ADR-0040 is language-neutral).

## Approach

One mechanism, many tools: a check is a command, a stage and optionally a
report; Specgate orders, runs, baselines, measures and reports, and the
project's build runs the tools. Diff coverage and mutation score are the two
measures Specgate computes itself, because no tool computes them per
requirement. Presets are data under `templates/quality/`, chosen by the stack
`harness init` already detects. The detail, per stack and per tool, is in
`design.md`.
